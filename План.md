## 1. Задача 1: прочистка параллельного корпуса

**Скрипт:** `scripts/01_clean.py` (CLI-параметры, все пороги настраиваемые).

Шаги (порядок фиксированный, каждый шаг пишет свой лог и свой промежуточный корпус):

1. `RAW` → `step1`: фильтр по длине. Удаляем пару, если в любой строке ≤ 2 слов (`len(s.split()) <= 2`). Дополнительно опциональный верхний предел (`--max-chars 600`) для хвостовых гигантов.
   Ожидаемо: −29 429 пар, лог `logs/01_short.log`.
2. `step1` → `step2`: фильтр по разнице длин в символах: `len(a) >= 2*len(b) or len(b) >= 2*len(a)`.
   Ожидаемо: −~2 200 чистых случаев (с учётом пересечений), лог `logs/02_len_ratio.log`.
3. `step2` → `step3`: доля алфавитных символов < 0.8 → удаление пары. Знаменатель — символы без пробелов; числитель — `c.isalpha()`. Отдельно поддерживается кириллический алфавит (множество `chr(1040)..chr(1103)`) как опция `--cyrillic-only` для выходной части, чтобы `ё` и не-ASCII символы не ломали метрику.
   Ожидаемо: −~4 300 пар с учётом пересечений, лог `logs/03_alpha.log`.
4. `step3` → `step4`: `fasttext-langdetect`: входная строка должна определяться как `en`, выходная — как `ru`. Логируем с пометкой `LANG_EN` / `LANG_RU`.
   Ожидаемо: несколько сотен – пара тысяч пар (Tatoeba чистый по языкам, но есть вкрапления).

Формат лога — как в ТЗ:
```
<ТИП_ОШИБКИ>
<строка_на_входном_языке>
<строка_на_выходном_языке>
```
Параллельность не нарушается: все фильтры применяются к паре целиком, строки читаются построчно и пишутся синхронно.

**Результат задачи 1:** `data/clean/Tatoeba.en-ru.en`, `data/clean/Tatoeba.en-ru.ru` (ожидаемо ~550k пар + минус языковой фильтр) и 4–5 логов + сводный `logs/summary.txt` с числами по каждому шагу.

Базовая проверка корректности: после каждого шага сверять `wc`-подобные счётчики (число строк в en == число строк в ru == число строк в логе × соответствующие группы).

## 2. Задача 2: скоринг параллельности и прочистка по скору

Основной путь (локально, GPU): **мультиязычные эмбеддинги `google/embeddinggemma-300m`**, косинусное сходство между векторами пары.

Скрипт `scripts/02_score_emb.py`:
- вход: пара файлов прочищенного корпуса (или `|||`-файл);
- батчи по 128–256 строк, `torch` на CUDA, fp16/bf16;
- выход: файл `scores.tsv` с колонками `score \t en \t ru`;
- 589k пар → на RTX 5070 ориентировочно десятки минут (2 прохода: en и ru стороны).

Анализ выдачи (скрипт `scripts/02_analyze.py`):
- сортировка по скору, гистограмма (ASCII-гистограмма + PNG при желании);
- квантили, границы 0.5/0.6/0.7/0.8/0.9 и «локоть» распределения;
- ручная проверка 25–30 пар около предполагаемой границы (выводим в `logs/threshold_review.txt`) — порог выбираем по здравому смыслу, не по одному эльбоу;
- фиксация порога в отчёте: например `score >= 0.65` (значение будет уточнено по фактически полученному распределению).

Прочистка: `step5` = пары выше порога, `logs/05_scores_below_threshold.log` с указанием скора для каждой удалённой пары (формат: `<SCORE_LOW> <score> \n en \n ru`).

Опциональные вторые пути (требуют Linux/Colab):
- **bicleaner** (классический, модель `en-ru.tar.gz` из bicleaner-data v1.6): `bicleaner-classify --model-dir ... -i en-ru.txt` → скор 0..1; хорошо валидирует эмбеддинговый скор.

## 4. Задача 4: файл выравнивания

Входной формат для fast_align/awesome-align: `en ||| ru` (одна строка на пару).
Получение: `paste file1 file2 | sed 's/ *\t */ ||| /g' > en-ru.txt` (Linux) или Python-эквивалент `scripts/04_make_paired.py` (локально, без shell-магии).

Вариант A (быстрый, локальный, без компиляции): **awesome-align** на mBERT.
- требует токенизации пробелами: `python awesome_align --forward --multi --input en-ru.tokenized --output forward.align` и обратное направление, затем grow-diag-final-and вручную (или только forward+reverse и простая объединяющая функция).
- Токенизацию делаем отдельным скриптом (`04_tokenize.py`): для выравнивания лучше word-level, а не SP-piece (piece-куски вида `▁sub` читаются хуже и искажают тип выравнивания `frag`).

Вариант B (канонический по ТЗ): **fast_align** в Colab/Linux:
```
./fast_align -i text.en-ru -d -o -v > forward.align
./fast_align -i text.en-ru -d -o -v -r > reverse.align
./atools -i forward.align -j reverse.align -c grow-diag-final-and > align
```
Компиляция по README: `git clone`, `mkdir build && cd build && cmake .. && make` (нужен g++).

Валидация: число строк в `align` равно числу пар; 20 выравниваний на глаз (`logs/06_align_review.txt`); тип выравнивания (`1`, `2`, `3`, `4`) распределён адекватно.

## 5. Задача 5: выделение случайной части

Скрипт `scripts/05_get_rand_sample.py`, аргументы через `sys.argv`:
```
python 05_get_rand_sample.py <N_строк_во_входном_корпусе> <нужное_кол_строк> <файл1> <файл2> [<файл3> ...]
```
Реализация:
- читаем все файлы в списки строк;
- проверяем, что длины совпадают с заявленным `N` (ошибка, если нет — это страховка от рассинхронизации параллельности);
- `idx = random.sample(range(N), k)` (один и тот же набор индексов для всех файлов → параллельность сохранена);
- фиксированный `--seed` (опционально) для воспроизводимости;
- выход: к каждому имени файла добавляется `.rand` (`Tatoeba.en-ru.en.rand`, `.ru.rand`, `.align.rand`).
- доп. проверка после записи: число строк во всех `.rand`-файлах равно `k`, и пары соответствуют друг другу (сверка по индексам).

Пример запуска на нашем корпусе: `python 05_get_rand_sample.py 554788 3000 data/clean/Tatoeba.en-ru.en data/clean/Tatoeba.en-ru.ru align/Tatoeba.en-ru.align`.

## Риски и как их обходить

- Компилируемые инструменты (fast_align, marian, bicleaner, kenlm) не собираются на этой машине: путь — Colab/Linux; локально их заменяем эмбеддингами (задача 2) и awesome-align (задача 4).
- `numpy<2` у COMET/bicleaner-ai конфликтует с Python 3.13: для них нужен Python 3.12 (или Colab).
- Гейты HF (Gemma, COMET): заранее завести токен и принять лицензии.
- Модель `fasttext-langdetect` скачивается при первом запуске: задать `FTLANG_CACHE` в рабочую папку, чтобы не зависеть от temp.
- Корпус содержит 52 полностью дублирующиеся пары и очень длинные строки (до 1127 символов): в задачи 1–2 добавить опции `--dedup` и `--max-chars`, решение фиксируем в отчёте.
- Если прочистка по эмбеддингам окажется слишком жёсткой (нижний порог режет нормальные пары) — понижаем порог и описываем это в `report.md` так же, как с пунктом 3 ТЗ.
